# Validate actual usefulness, not just visual appeal

No user/customer study has been conducted for this product by the planner. No purchase/sales claim follows from the package. Competency-based education is a rationale for task-oriented design, not proof of this app's effectiveness or market demand. Reference: https://pharmacyeducation.fip.org/pharmacyeducation/article/view/2149 .

When a usable build and participants are available, run the original5–8 formative participant study with learners/instructors, documenting actual device/build/model/mode and consent/anonymous IDs. Ask learners to perform a defined supported preparation/transfer/reading procedure, explain a resulting change and locate/review an error. Observe completion, missed selections, reading errors, unwanted actuation, assistance and recovery.
Ask an instructor to configure a supported lesson, preview it and review an attempt. Record whether the evidence allows useful feedback and how the activity fits an actual course. Compare responses to concrete task goals; no forced positive answers. Record actual willingness to trial/purchase only if explicitly expressed; no fictional pricing or sales forecast.

Distinguish device comfort, technique transfer, conceptual understanding and product usability. A successful software test does not establish learning gains. A later educational outcome study needs its own design, comparator and analysis; do not report improvement without measurement. Missing participants leaves this evidence pending while independent software work continues.
